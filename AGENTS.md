# AGENTS.md

Repo root = `vcte5000/`. All path-relative commands below assume this as the working directory.

## Architecture

- **`backend/`** — Django 4.2.8 ERP (server-rendered + HTMX middleware). **`frontend/`** — Vue 3 + Vite 5 + Tailwind CSS 3 SPA → builds into `backend/static/web/` (base path `/static/web/`); dev server :3000 proxies `/api` + `/media` → :8000.
- `docker-compose.yml`: 5 services — `db` (Postgres 15), `redis`, `backend`, `celery_worker`, `nginx`.
- Python 3.11.9 (`.python-version`). 12 backend apps under `apps/` — import as `apps.<name>`. `apps.api` is **not** in `INSTALLED_APPS` but works because its `urls.py` is imported directly. `apps.payroll` also exists (route `/erp/nominas/`).
- `soportes madrid/` — sample PDF/CSV supporting documents (facturas, extractos bancarios) used by test and simulation scripts.
- `backend/manual/` — user manuals (`manual.html` full manual, `roger.html` operator view). The §20 pipeline scripts (root `test_pipeline_capitulo20.py`, `simulacion_capitulo20.py`) implement "capítulo 20" of that manual.
- Utility scripts (root unless noted): `create_test_purchase.py` (seeds catalog materials + multi-material `CompraMaterial`), `fix_inversion_banco.py` (one-off `InversionInicial` bank repair; header has the staging variant), `backend/create_missing_warranties.py` (backfills `GarantiaVehiculo` for existing sales), `backend/generate_manual.py` / `generate_manual_xhtml2pdf.py` (regenerate `media/manual_eurocar_erp.pdf`; on this Windows machine weasyprint lacks GTK libs — use `generate_manual_xhtml2pdf.py`), `backend/manual/ejemplos/gen_soportes_madrid.py` (regenerates the `soportes madrid/` capítulo-20 PDFs). CLI uploads: `manage.py subir_factura_gasto --pk <id> --pdf <file>` (adjunta factura de proveedor a un `GastoEstructura`), `manage.py subir_imagen_vehiculo --matricula <m> --imagen <file>` (solo `EN_VENTA`).
- Settings in `config/settings/`: `development` (default; SQLite unless `DATABASE_URL`), `staging` (no Redis: locmem cache, Celery eager, WhiteNoise; media local/ephemeral on purpose), `production` (S3 media only if `AWS_STORAGE_BUCKET_NAME`; Redis optional → locmem + eager fallback). Root test scripts set `DJANGO_SETTINGS_MODULE=config.settings.development` themselves.
- Root `README.md` is generic marketing and partially stale (says `cd eurocar`; repo dir is `vcte5000`) — trust this file and the code over it.

Routing (`backend/config/urls.py:7-28`): ERP under `/erp/*`, API at `/api/`, admin at `/admin/`. **Catch-all `spa_index` must stay last** — serves the Vue SPA for unmatched paths.

Frontend CSS changes require a full `npm run build` (Vite → PostCSS → Tailwind). The dev server uses HMR for JS/Vue but can miss Tailwind-only rebuilds.

Agent instruction sources beyond this file: `.claude/skills/` contains TestSprite skills (`testsprite-onboard`, `testsprite-verify`) for automated test generation and verification workflows.

## Key views

- **`/api/*` dual-mode**: returns HTML when `Accept: text/html`, else JSON (`apps/api/urls.py:11` `is_html_request`). Keep both branches working.
- **`/api/*` is fully anonymous**: no DRF viewsets — hand-rolled function views only (`apps/api/urls.py:197-203`): `health/`, `ping/` (plain "OK", no DB), `vehiculos/`, `vehiculos/<pk>/`, `marcas/` (listings filtered to `EN_VENTA` + `precio_venta>0`). DRF's `IsAuthenticated` default doesn't apply to function views; `test_modules.py` asserts `/api/vehiculos/` → 200 unauthenticated — don't "protect" them. El listado devuelve `imagen_url` (portada) **y** `imagenes_urls` (galería ordenada) para el carrusel de las tarjetas; el detalle devuelve `imagenes: [{url, es_principal, orden}]`. Las tarjetas del catálogo y de la home usan `aspect-[4/3]` + `object-cover`, con `loading="lazy"` salvo la portada.
- **SPA works only after `npm run build`**: `spa_index` serves `STATIC_ROOT/web/index.html`, else 404 "Web pública no construida" (`apps/core/views.py:94-100`). Build artifacts (`backend/static/web/`) are git-ignored but **force-committed** (`git add -f`) so the public catalog works at `/` on Render — after ANY frontend change, rebuild and re-commit them. Deep links (`/catalogo`, `/vehiculo/<id>`, `/tasacion`, `/contacto`) hit the `spa_index` catch-all (vue-router history mode).
- **Roles** (`accounts.User.rol`): `ADMIN`, `OPERARIO`, `VENDEDOR`, `GESTORIA`. Use `user.is_admin` / `is_operario` / `is_vendedor` / `is_gestoria` properties — never raw `rol` comparisons.
- **Usuarios en el ERP**: `apps/accounts/views_usuarios.py` + `urls_usuarios.py` sirven `/erp/usuarios/` (listado, alta, edición, activar/desactivar, desbloquear), solo para `is_admin`. El enlace del sidebar «👥 Usuarios» apunta ahí; «⚙️ Admin técnico» sigue siendo el admin de Django. Un ADMIN no puede desactivarse a sí mismo.

## Gotchas

- **Custom User** = `accounts.User` (`AUTH_USER_MODEL`). Import from `apps.accounts.models`, never `django.contrib.auth`.
- **`User.puede_eliminar`** (default True) gates delete permission. `rol` default is `'OPERARIO'` (`accounts/models.py:19`); migration `0003_alter_user_rol` briefly set the DB default to `'ADMIN'` and `0004_alter_user_rol` aligned it back to `'OPERARIO'` — if you add another `AlterField`, keep the model default in sync. The login view auto-repairs empty `rol` to `'ADMIN'` for staff users. `is_admin`/`is_operario`/`is_vendedor`/`is_gestoria` properties also return True for any `is_superuser`, so a `createsuperuser` user passes every role check.
- **Keep `base.py:5-14` monkey-patch** of `BaseContext.__copy__` (Python 3.14 compat even though we run 3.11).
- **`development.py` desactiva explícitamente HTTPS/HSTS** (`SECURE_SSL_REDIRECT=False`, cookies no `Secure`). `base.py` aplica los ajustes de producción cuando el entorno no define `DEBUG`, y un clon sin `backend/.env` provocaría un 301 a HTTPS en el servidor de desarrollo. No quitar ese bloque.
- **`debug_toolbar` removed** — incompatible with Python 3.14. Don't re-add.
- **`.env` split**: `backend/.env` is read by Django (`base.py:23`) y **ya no está versionado** (salió de git; plantilla en `backend/.env.example`). Root `.env.example` is for docker-compose only.
- **Spanish number formats**: `base.py` sets `USE_THOUSAND_SEPARATOR=True` + `FORMAT_MODULE_PATH=['config.formats']` (`config/formats/es/formats.py`: `.` thousands, `,` decimals → `8.294,00`). Templates render amounts in this format; tests asserting exact amount strings must match it.
- **Media en staging vs producción**: `config/urls.py` registra siempre `^media/(?P<path>.*)$` y la vista solo responde si `DEBUG` o `SERVE_MEDIA_LOCAL`. En `staging.py` vale `True` (sin bucket, los PDFs se abren durante las pruebas desde el disco del contenedor, que **se borra en cada redeploy**). En `production.py` vale `False`: la media debe ir a S3/R2. Sin esa ruta, con `DEBUG=False` cualquier adjunto daba 404.
- **Plan contable automático**: `apps/accounting/apps.py` conecta `post_migrate` y crea el PGC (56 cuentas, `get_or_create`) en cada `migrate`. La vista `bank:cuenta_create` lo recrea si está vacío, para que el desplegable «Cuenta contable» nunca aparezca vacío. El botón «Inicializar PGC» se retiró de la interfaz; el endpoint queda solo para mantenimiento y scripts.
- **Dual account locking**: manual (5 attempts → 1h lock) + `django-axes` (`AXES_FAILURE_LIMIT=5`, `AXES_COOLOFF_TIME=1`). Both active.
- **`django-csp`** in `INSTALLED_APPS` (no custom `CSP_*` settings). Default CSP blocks inline `<script>`/`<style>` — use nonces or external files.
- **PDFs** (`apps/sales/services.py`): motor perezoso — WeasyPrint si sus librerías de sistema (Pango/Cairo) cargan; si no, `xhtml2pdf` (Python puro, el que funciona en el runtime nativo de Render, que no instala paquetes del sistema). Los PDFs se guardan vía `FileField`/`default_storage`, nunca escribiendo a `MEDIA_ROOT` a mano, para que funcionen igual con disco local y con S3/R2.
- **Session**: expires in 1h and on browser close. `SESSION_SAVE_EVERY_REQUEST=True`.
- **`django-cleanup`** auto-deletes orphaned files when records are removed.
- **Development** has `AUTH_PASSWORD_VALIDATORS = []` — weak passwords work locally but not in production.
- **`SECRET_KEY` has no default** (`base.py:25`) — local Django runs fail without `backend/.env`; Docker works zero-config (compose supplies an insecure dev fallback). Several migrations (e.g. accounts `0003`, vehicles `0007`) were generated by Django 6.0.7 — never run `makemigrations` with anything newer than the pinned 4.2.8.
- **Production degrades gracefully without Redis** (`production.py`): if the `REDIS_URL` env var is absent, cache falls back to locmem and `CELERY_TASK_ALWAYS_EAGER=True` + broker/result `None` (same pattern as staging). Set `REDIS_URL` on Render only if a Redis instance is actually provisioned.
- **Control de saldo por fecha (tesorería)**: `crear_movimiento_banco()` rechaza cualquier **EGRESO** si `importe > banco_cuenta.saldo_a_fecha(fecha)` (ingresos − egresos con fecha ≤ la del pago; **no** usa el saldo de hoy) con `ValidationError`: «Saldo insuficiente en la cuenta bancaria en la fecha indicada (Saldo disponible: X). Registre primero el ingreso/depósito». Helper `validar_saldo_egreso(cuenta, fecha, importe)` para pre-validar. Se valida antes de guardar en la compra de vehículo (`_error_saldo_compra_vehiculo` en `vehicles/views.py`), en compras de taller (`_error_saldo_banco`, con `fecha_pago`/`fecha_compra`), en pagos de gastos (si falla se deshace `pagado`) y en devoluciones de reserva; la caja 570 no genera movimiento y no se valida. Los INGRESOS retroactivos sí se permiten. **Bank movements** are never created manually — `apps.bank.services.crear_movimiento_banco()` is the single entry point, y va **decorada con `@transaction.atomic`**: usa `select_for_update()` sobre la cuenta y, en PostgreSQL, fuera de una transacción lanza `TransactionManagementError` (era el 500 al crear la primera cuenta bancaria con depósito inicial: la cuenta quedaba guardada y el reintento avisaba de IBAN duplicado). `bank:cuenta_create` y `bank:deposito_create` son atómicas y enlazan el movimiento con su asiento (`asiento_asociado`); `BancoCuenta.saldo` is computed on-the-fly. All reconciliation logic (`conciliar_extracto`, `conciliacion_bancaria_sugerencias`, `marcar_conciliado`, `conciliacion_batch`) lives in `apps/bank/services.py`.
- **Catálogo público: vendidos visibles 30 días**: `Vehiculo.fecha_vendido` (migración `vehicles/0009`) se fija sola al pasar a **VENDIDO** y se limpia al volver a publicarse (en `Vehiculo.save()`, que añade el campo a `update_fields`). `Vehiculo.visibles_en_web()` devuelve `EN_VENTA` con precio **más** `VENDIDO` con `fecha_vendido >= hoy - DIAS_VISIBLE_VENDIDO (30)`; lo usan `/api/vehiculos/`, `/api/vehiculos/<pk>/` y `/api/marcas/`, y el JSON lleva `vendido: true`. La SPA pinta el cintillo «VENDIDO» sobre la foto (tarjetas y ficha) y en la ficha sustituye «Pedir cita» por «Consultar disponibilidad de similares». Pasados 30 días desaparece solo, sin cron; las fotos siguen en el ERP. - **Fotos rotas en staging**: la media del staging es **efímera** (sin bucket R2 se pierde en cada redeploy); las filas `ImagenVehiculo`/`imagen_principal` quedan y las URLs dan 404 (la web muestra «Imagen 1, Imagen 2...»). Vender o anular una venta **no** toca las fotos (lo garantiza `ImagenesAlVenderYAnularTests`); el problema es el disco. Diagnóstico: `python manage.py comprobar_imagenes_vehiculos` lista los archivos perdidos; `--borrar-huerfanas` limpia las referencias rotas (después hay que volver a subirlas desde 📢 Publicar). Solución definitiva: configurar `AWS_STORAGE_BUCKET_NAME` (R2). El kilometraje público se formatea con `formatKm()` de `frontend/src/utils/format.js` (95.000 km). - **Vehicle images**: uploads only allowed while `estado='EN_VENTA'`; al salir de `EN_VENTA` las fotos **se conservan** (ocultas, reaparecen al volver) — antes se borraban en silencio. Tope **15 adicionales + 1 principal** (`MAX_IMAGENES` en `apps/vehicles/forms.py`); el formset **avisa** si se supera en vez de recortar en silencio. Toda subida pasa por `apps/vehicles/images.py`: reduce a 2560 px, recomprime en JPEG q85, descarta EXIF y guarda en `vehiculos/<matricula>/`. El campo `ImagenVehiculo.es_principal` sigue en BD pero **no se usa** (la portada es `Vehiculo.imagen_principal`). Procedimiento de usuario: manual capítulo 22.
- **Vehículos: dos hojas y contabilidad automática**. Sin campos repetidos: `vehicles:update`/`create` (hoja 1, `form.html`) solo lleva técnicos + adquisición + costes (`precio_subasta`, `tasas_sala`, `logistica_grua`, `tipo_iva`, `forma_pago`) + factura de compra; `vehicles:publicar` (hoja 2, `publicar.html` con `VehiculoComercialForm`) solo estado, precio de venta, **fecha de publicación** (`Vehiculo.fecha_publicacion`, migración `vehicles/0008`: se fija sola con `timezone.localdate()` al pasar a EN_VENTA si está vacía, es editable y `clean_fecha_publicacion` conserva la existente si el campo llega vacío; propiedad `dias_en_venta`), descripción, portada y formset de fotos (botón **Quitar** en `vehiculo-publicar.js`), accesible también al rol VENDEDOR y **sin tocar costes**. La ficha (`detail.html`) muestra un bloque «Datos comerciales» con precio, fecha de publicación y botón **✏️ Editar** que abre esta hoja. **Al guardar la hoja 1**, `_regenerar_asiento_compra()` se ejecuta **siempre**: anula el asiento anterior **con contrapartida** (Ley Antifraude, queda ANULADO), crea y postea uno nuevo con los importes guardados y regenera el movimiento bancario (sin comparaciones ni mensajes de «no han cambiado»). `Vehiculo.save()` tolera importes `None` (los trata como 0). **Importes**: `ImporteField`+`parsear_importe()` aceptan `7.500,00`, `7500,00`, `7500.00` y `7500` sin ambigüedad (con coma los puntos son miles; **un único punto con 3 cifras también es separador de miles: `7.500` → 7500**) y `localize=True` los renderiza en español; `fecha_adquisicion` usa `DateInput(format='%Y-%m-%d')`. El JS `static/js/vehiculo-costes.js` formatea **al salir del campo y antes de enviar**, nunca mientras se escribe, **bloquea el envío implícito con Enter** (`keydown` en el formulario salvo textarea/botones) y desactiva Guardar tras enviar; su `parseValor()` aplica la misma regla de desambiguación. **`ImagenVehiculoForm.clean_imagen` solo procesa archivos recién subidos** (`isinstance(archivo, UploadedFile)`): re-procesar un `FieldFile` ya guardado fallaba con `FileNotFoundError` si el archivo se perdió en un despliegue. La miniatura usa `ImagenVehiculoForm.url_actual()`. **Reparación de importes corruptos** (bug antiguo ×10.000): `python manage.py corregir_coste_vehiculo <matricula> --precio-subasta 7500 --tasas 400 --grua 250 [--tipo-iva 136.50]` corrige los importes, anula por contrapartida el asiento anterior y crea uno nuevo posteado (`--sin-asiento` para no tocar contabilidad).
- **Alta de OT: dos accesos, una sola vista**: tanto «Taller → ➕ Nueva OT» como «Vehículo → ficha → + Nueva OT» usan `workshop:create_ot` (`orden_trabajo_create`) y la plantilla `workshop/form.html`; el segundo añade `?vehiculo=<pk>` y el vehículo llega **preseleccionado** (`initial`). Al crear la OT, si el vehículo está **ADQUIRIDO** pasa a **TALLER**; los vehículos **VENDIDO** se excluyen del desplegable (salvo el de una OT que se edita) y avisan si se intenta precargar. Si el usuario **sube un PDF nuevo** en la corrección, se usa ese directamente y no se lee el anterior. Ojo con el nombre: `django-cleanup` borra los archivos de las filas eliminadas al **confirmar la transacción**, así que `_nombre_pdf_sin_colision()` renombra el PDF nuevo (`_corregida_xxxxxx`) cuando reutiliza el nombre del antiguo; sin eso, la limpieza diferida borraba también el archivo recién subido y la factura quedaba con «PDF no disponible». - **Reserva con datos fiscales y factura de anticipo**: `bank.Reserva` guarda `tipo_cliente`, `cliente_direccion/poblacion/provincia/cp/telefono/email` y `metodo_pago` (migración `bank/0010`), obligatorios en `ReservaForm` salvo el email. `bank.FacturaReserva` (OneToOne, `related_name='factura'`) numera **correlativo por año** con `generar_siguiente_codigo()` (`A-2026-0001`); la vista `bank:reserva_factura` la emite una sola vez, genera el PDF con `bank/services.generar_pdf_factura_reserva()` (plantilla `bank/factura_reserva.html`, reutiliza `EMPRESA` y `_render_pdf` de `sales.services`) y lo sirve inline; si el archivo ya existe, lo reutiliza. La factura **no desglosa IVA**: lleva la nota REBU de entrega a cuenta. `venta_create` precarga el formulario de venta con los datos fiscales de la reserva y sigue descontando la señal. - **Reservas (señal) y venta**: `apps.bank.Reserva` guarda la señal con su movimiento bancario y su asiento; al ser **entrega a cuenta REBU** el importe íntegro va a **438** (DEBE 572 / HABER 438), **sin IVA propio**, y se cancela completo en el asiento de la venta (la 477 no interviene; el IVA va en 471 sobre el margen). `reserva_create` lo **postea** si cuadra y lo **enlaza** al movimiento (`movimiento.asiento_asociado`), con `vehiculo_asociado` para poder rastrearlo desde el banco. `reserva_convertir` lleva a `/erp/ventas/nueva/?vehiculo=..&reserva=..`.

No se permiten dos reservas ACTIVA del mismo vehículo. No se puede rectificar una rectificativa (ValueError). - **Un vehículo puede tener varias ventas (histórico)**: `VentaVehiculo.vehiculo` es **FK** (`related_name='ventas'`, `sales/0010`) con una `UniqueConstraint` **condicional** (`condition=Q(anulada=False)`): solo una venta vigente por coche, pero las anuladas se conservan y no bloquean una reventa. `Vehiculo.venta` es una **propiedad** que devuelve la última venta no anulada (sustituye a la antigua OneToOne; las plantillas siguen funcionando). `venta_create` avisa si el vehículo ya tiene una venta activa. `DetalleRebu.vehiculo` también pasó a **FK** (`sales/0009`) con unicidad `(factura, vehiculo)`: una rectificativa o una segunda venta ya no chocan con `sales_detallerebu_vehiculo_id_key`. - **Anular vs eliminar una venta**: `sales:anular` (`venta_anular`) es el camino normal: conserva la venta (`VentaVehiculo.anulada`, `fecha_anulacion`, `motivo_anulacion`, `anulada_por`, migración `sales/0007`), anula el asiento con contrapartida (`AnulacionVenta`), **compensa** el cobro con un EGRESO (no lo borra), reactiva la reserva, devuelve el vehículo a EN_VENTA y, si había factura, emite una **rectificativa R1** con su PDF (la original se conserva). `sales:delete` queda solo para **borradores sin asiento, cobro ni factura**; si tiene movimientos responde con un aviso que remite a «Anular venta» (sin 500). `FacturaVenta.venta` es opcional (`sales/0008`) porque la rectificativa se vincula a la factura original; `FacturaVenta.vehiculo` resuelve el vehículo en ambos casos. `_revertir_venta()` es el helper común (asiento + banco + reserva + vehículo); `_anular_venta()` marca y `_deshacer_venta()` borra el borrador. - **Eliminar una venta**: `venta_delete` ya no lanza 500. Si la venta tiene factura REBU pide confirmación expresa (`eliminar_factura`) y avisa de que en producción lo correcto es una rectificativa; al confirmar borra la venta. `_deshacer_venta()` anula el asiento **con contrapartida** (ANULADO, no se borra), elimina el INGRESO de la venta en Banco (la señal permanece), devuelve la reserva CONVERTIDA a ACTIVA y el vehículo a EN_VENTA; cualquier `ProtectedError` se muestra como mensaje rojo. - **Cobro de la venta en Banco**: `venta_create` registra venta + asiento + cobro en una sola transacción: si falla el asiento o el movimiento, **no se guarda nada** y sale error rojo (antes la venta quedaba sin ingreso y solo un aviso amarillo: bug V-2). `VentaVehiculo.registrar_movimiento_banco()` crea el INGRESO por `precio_venta − señal`, no crea nada si `metodo_pago=='FINANCIADO'` y lanza `ValidationError` si no hay cuenta activa (ya no se omite en silencio). La ficha de la venta muestra un bloque «Cobro en banco» con la señal y el cobro; si falta, avisa con el comando de reparación: `python manage.py reparar_cobro_venta --venta <pk>` (`--matricula`, `--todas`, `--dry-run`), que no duplica si el ingreso ya existe. - **Sales payments** (`CobroFraccionado`, migration `sales/0006`): plazos go PENDIENTE→RECIBIDO; `cobro_recibir` calls `CobroFraccionado.recibir()` which generates the asiento. `VentaVehiculo.pagada` auto-flips when `total_cobrado >= precio_venta` (recomputed from RECIBIDO cobros).
- **Stray git-tracked logs**: `backend/server_out.txt` / `server_err.txt` are leftover local runserver output dumps, not config — ignore or delete them. `backend/test_staging.db` is a stray SQLite file (git-ignored), same treatment.

- **Docker Postgres password**: compose substitutes `POSTGRES_*`/`SECRET_KEY` from shell vars or root `.env`; this machine runs `--env-file .env.production` (`POSTGRES_DB=eurocar_prod`, password ≠ compose default `eurocar_dev_2024`). ## Production Deploy

Deployed on **Render** (Python runtime, not Docker). Self-hosted alternative: `docker-compose.prod.yml`. Render build: `pip install -r requirements.txt && python manage.py collectstatic --no-input && python manage.py migrate`. Start: `gunicorn config.wsgi:application --bind 0.0.0.0:8000 --workers 2 --timeout 120`.

- **Two deploy targets**: `render.yaml` defines the **staging** service (branch `staging`, `DJANGO_SETTINGS_MODULE=config.settings.staging`). `master` is the main branch (`origin/HEAD` → `master`); production deploys from it via the Render dashboard (not in-repo, **no auto-deploy** — push alone does not deploy production). The current repo branch is `staging`.
- **Render (situación actual)**: staging está desplegado en **https://staging.rogil.co** — servicio `eurocar-staging` (rama `staging`, plan free, región Fráncfort), base `rogil-db-staging` (gratuita, caduca a los ~30 días) y media local/ephemeral. **No hay producción**: la cuenta de Render no tiene método de pago y el bloque de producción de `render.yaml` está comentado; reactivarlo cuando exista tarjeta. Los servicios antiguos `eurocar-jdx2.onrender.com` / `eurocar-staging-jdx2.onrender.com` **ya no existen** (404): no usarlos ni buscarlos. El dominio `rogil.co` está en Cloudflare (Namecheap como registrador); `rcarrogil.com` queda para cuando se libere.
- **`docker-compose.prod.yml` (self-hosted)** requires: `.env.production` (see `.env.production.example` — must include `DJANGO_SETTINGS_MODULE=config.settings.production`, else `wsgi.py`/`celery.py` default to development), SSL certs in `docker/nginx/ssl/` (`fullchain.pem` + `privkey.pem`), `docker/nginx/prod.conf` (HTTP→HTTPS redirect). Backend runs `migrate` + `collectstatic` at boot; SPA is built inside `backend/Dockerfile.prod` (no `vue_data` volume — an empty named volume would shadow the built SPA).
- **Env vars by environment**: dev = `backend/.env` (`SECRET_KEY` mandatory). Staging/Render = `SECRET_KEY`, `DATABASE_URL`, `DEBUG`, `ALLOWED_HOSTS` (in `render.yaml`); no `REDIS_URL`/`AWS_*`. Production/Render (manual §12.5-12.6) = same + `AWS_*` (R2 media) + `EMAIL_*` (SMTP); `REDIS_URL` optional (graceful fallback). Opcionales para cambiar de dominio sin tocar código: `CSRF_TRUSTED_ORIGINS` y `HSTS_PRELOAD=false` (ver `PRODUCCION.md` §7).
- **Staging media**: `staging.py` no exige bucket (por defecto, disco local efímero) pero **sí activa S3/R2 si existe `AWS_STORAGE_BUCKET_NAME`**, para probar la persistencia antes de producción. Mientras no haya bucket, `SERVE_MEDIA_LOCAL=True` permite abrir los PDFs (se pierden en cada redeploy). The SPA artifacts (`backend/static/web/`) are committed, so the public catalog serves at `/` on staging/prod; keep `collectstatic` in the Render build (it copies `static/web/` into `staticfiles/web/` for `spa_index`).
- **WhiteNoise without manifest**: `STATICFILES_STORAGE = CompressedStaticFilesStorage` (staging + production) — intentional. The Vite `index.html` references assets by name (`/static/web/assets/...`); the manifest storage renames files and would break the SPA. Django's own statics lose hash cache-busting (cosmetic).
- **Staging quirks** (`config/settings/staging.py`): Celery tasks run eagerly/sync — don't assume a Celery worker or Redis-backed cache there.
- **Auto-Deploy**: push to the service's configured branch. If a push doesn't go live, click **Manual Deploy → Clear build cache & deploy**.
- **Ephemeral filesystem**: uploaded media lost on redeploy. **Guía paso a paso: [`GUIA_R2.md`](GUIA_R2.md)** (bucket público, token Object Read & Write, seis variables `AWS_*` en Render). Persist via R2 (set `AWS_STORAGE_BUCKET_NAME` to activate `storages.backends.s3.S3Storage` in `production.py:33`). Bucket must be public (`AWS_QUERYSTRING_AUTH=False`).
- **Limpiar staging**: `python manage.py limpiar_datos_prueba` (sin `--confirmar` solo simula) borra vehículos, ventas, compras, OTs, gastos, nóminas, marcajes, banco y asientos, **conservando usuarios, plan contable y tareas de Celery**; con los ajustes de producción exige `--forzar`. Hacer antes un `pg_dump`. No usar `flush` (borraría también los usuarios).
- UptimeRobot pings `https://<app>.onrender.com/api/ping/` every 10 min to avoid cold starts (`/api/ping/` returns plain-text "OK", no DB access — also Render's `healthCheckPath`). DB backed up daily by `.github/workflows/backup.yml`.
